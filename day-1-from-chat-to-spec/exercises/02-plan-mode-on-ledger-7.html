Reference answers

Open these after your run; the fix is not in them. The same three sections are in the repository, reached from starter/answers/e2-plan-checklist.md, which points at plan-checklist.md beside it.

What a passing answer looks like for each of the six items

1. The file it will change. Yes looks like Sources/LedgerKit/Money.swift, or src/main/kotlin/ledgerkit/Money.kt, written out once as a path. No looks like “update the money formatting logic”: true, and it does not tell you whether one file or three is about to move. A plan naming two files fails this item only if it does not say what each one gets.

2. Each currency and its minor-unit count. Yes looks like the five codes with their counts in the plan text, before any code is written. No looks like “give JPY zero decimal places”, which fixes the ticket and leaves you no way to tell whether the other four are about to change by accident. This is the item most first plans fail, because the ticket mentions one currency and the plan mirrors the ticket.

3. The exact verification command. Yes looks like swift test or ./gradlew test spelled out, plus what counts as success. No looks like “run the tests to confirm”, which a sentence in the final message can satisfy.

4. How the gated test gets run. Yes looks like the gated command named as a step of its own. No looks like silence, and silence is the expensive answer here: the suite is green before the fix and green after it, so a plan that only runs the plain command has verified nothing about the bug.

5. Staying out of LedgerSummary and the fixture. Yes looks like no step touching either, and ideally a line saying so. No looks like a step that edits the fixture or “updates the expected value”: the fixture already holds the right answer, so a plan proposing to change it has decided the bug is in the test.

6. What it will not change. Yes looks like one line naming the neighbours it is leaving alone. Most plans have no such line unless the prompt asks for one, which is why the prompt asks for one. It is the cheapest signal you get about whether the boundary was understood or is going to be discovered halfway through.

The two rejection sentences the reference run sent

Rejection 1, against a plan that failed item 4:

Swift lane 
Item 4: the plan verifies with swift test only, which is green before and
after the fix. Name the gated command as a separate step and say what its
output is before the change and after it.
Kotlin lane 
Item 4: the plan verifies with ./gradlew test only, which is green before
and after the fix. Name the gated command as a separate step and say what
its output is before the change and after it.

Rejection 2, against a plan that passed all six, so it was rejected on the weakest item:

Item 2: you list JPY at zero but not the other four. Put USD, EUR, GBP and
BHD in the plan with their counts so I can see at review time that the
table is complete rather than patched.

The second one is the skill this exercise is teaching. That plan was not wrong; it was reviewable in principle rather than reviewable in ten seconds, and saying so cost one sentence. A rejection that names no item number and no missing thing is not a rejection, it is a mood, and “this needs more detail” sends the agent to guess which detail.

These are the five currencies the fixture uses, and its expectedAmountText column already holds every string in the right-hand column. BHD surprises people twice: three decimal places is correct, and the ticket's second complaint is about how it reads, not about whether it is right.
