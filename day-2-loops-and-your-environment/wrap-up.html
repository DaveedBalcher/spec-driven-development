What you learned

  • Drift is a bookkeeping gap, not a model failure. It enters at four moments, spec to plan, plan to diff, diff to tests, and run to run, each with a detector that costs under a minute.
  • Guides push instructions forward; sensors report back, and a sensor fails loudly where guidance is ignored quietly.
  • A runner is a skill file, .claude/skills/run-spec/SKILL.md, invoked as /run-spec, with three exits: green, the iteration cap, or a gate. A gate is a question, the evidence to answer it in under a minute, and two or three answers.
  • The loop's memory is the filesystem. One line per iteration in run-log.md survives a compaction, a /clear and tomorrow morning; a transcript survives none of them.
  • Improvement runs in three rings: the output, the instructions, the workflow. A finding tagged to an existing criterion is ring one: fix the code. Most NO-CRITERION findings become a new or sharpened acceptance criterion; the rest become a line in the standing instructions, under the net-zero line cap, for a fact that outlives this change, or go in the bin with one sentence saying why. Only the outer ring owes a measurement: re-run from a fresh copy and compare iteration counts, or do not claim the workflow got better.
  • The critic, .claude/agents/spec-auditor.md, is a subagent that starts with a fresh, isolated context window, and its tools: line holds it to reading.
  • Read-only is a property of how a connector was deployed, not a promise a prompt can make. Permission rules, written Tool(pattern), are evaluated deny, then ask, then allow, the first match winning regardless of specificity.
  • Writes leave through one wrapper that holds the credential, checks an allowlist, dry-runs, confirms and logs; a change to it goes by pull request, and the reviewer asks what the allowlist now permits that it did not. .claude/settings.json is shared, .claude/settings.local.json is yours, and promoting a rule from the second to the first makes your habit the team's.

Challenges

No reveals, no solutions; one is enough.

1. A gate on quality, not correctness

The gate you wrote in Exercise 1 was mechanical: a count, a file list. Replace it with one that fires when a new test asserts the behavior the code has rather than the behavior the spec names, which the runner can only judge by reading intent. Write its question, evidence and answers, then run Change B (Exercise 1's spec) in a fresh day2-work and see whether it fires on a run you would have accepted.

2. Three runs, and what three runs prove

Run the same spec three times, each in a fresh day2-work, with three CLAUDE.md variants and everything else identical: the shipped file, the shipped file plus one line you would add after today, and the shipped file minus one line you think does no work. Copy each run-log.md into ../work/ before the next reset. Write five sentences on what n = 3 does and does not let you conclude, including what changed between runs that you did not control.

3. An auditor you can trust twice

Tune .claude/agents/spec-auditor.md until it catches all six reference findings from Exercise 2 (the defects in the finished run its catch-up block copies in) and returns nothing on a change you already accepted. Record which single change did the most work.
