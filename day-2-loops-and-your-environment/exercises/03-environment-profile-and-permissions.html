Steps

  1. Fill the six rows of env-profile.md, one short true sentence each. Start from the Default wording column of its table and change what is false for you. Name the kind of connector, not the vendor: no employer, internal system, hostname or repository name. A connector that later needs a rule of its own is scoped as mcp__<server>, mcp__<server>__*, or mcp__<server>__<tool>.

  2. Edit .claude/settings.json: the deny list first, then ask, then allow, which is the order the engine evaluates rules in. Each rule is shaped Tool(pattern). Keep every shipped rule, including any allow rule you cannot yet justify; step 4 and the reference answers come back to those. You may add rules, but write no allow rule of your own you cannot justify in one sentence. The only rules you remove are the other lane's two allow rules (Bash(swift test:*) and Edit(./Sources/**) for Kotlin, Bash(./gradlew test) and Edit(./src/**) for Swift), since the example carries both lanes' and those match nothing in your copy. Leave settings.example.md closed until your predictions exist.

  3. Fill all six rows of prediction-grid.md before you run anything. For each command write allow, ask or deny, and name the rule you think decides it. Predictions written afterwards teach nothing.

If you see something else instead

Likely wrong turns

  • A line naming a line and a column where the reformatted file should be. A comma left after the last deny rule printed Illegal trailing comma before end of array: line 14 column 25 (char 309) under Python 3.14 on 2026-09-23; the wording varies by version. The file is malformed: fix it and check again before you start a session.
  • The agent runs rm -rf build without stopping. The deny rule covering rm is not among the rules this session loaded: it came out during your edit, or the session started outside day2-work and read a different .claude/settings.json. Quit, run step 4's checks, start again.
  • /permissions shows rules you never wrote. Something above your file has an opinion. Settings resolve in a fixed order: a managed managed-settings.json from MDM or the console, then claude --settings, then .claude/settings.local.json, then .claude/settings.json, then ~/.claude/settings.json.
  • You chose “Yes, and don't ask again” on row 3. Record the row as ask anyway. The rule went into a .claude/settings.local.json, not the file you edited; the reveal says where that file is and what the rule changes. /permissions shows it.

Self-check

Four lines decide it

The fourth prints 0 unless you wrote a gh pr view rule yourself in step 2, because an accepted “don't ask again” is never saved to the shared file, wherever its settings.local.json ended up.

Reference answers

Row 5, and the rule row 3 can leave behind

Row 5, rm -rf build. This is the row built to disagree with a first reading of the file. The example allows Bash(rm -rf build) and denies Bash(rm:*). The allow rule reads as housekeeping and does nothing: evaluation runs deny, then ask, then allow, and the first match ends the decision regardless of how specific a later rule is. Specificity is never a tiebreak. The row is deny, decided by Bash(rm:*), and the narrow allow underneath it never runs.

That is the failure mode worth carrying out of this exercise. A rule that is written, read in review, and approved can still be inert, and nothing in the file says so. The only way to know is to predict a command and then run it. Row 4, gh pr merge 1, is the same mechanism pointing the way people expect: Bash(gh pr merge:*) in the deny list settles it before the Bash(gh:*) ask rule is ever consulted.

Row 3, gh pr view 1. The row is ask, decided by Bash(gh:*). The rule to watch is the one an accepted “Yes, and don't ask again” saves. It is an allow rule, and in day2-work it changes nothing: the ask rule Bash(gh:*) is evaluated first, the same mechanism as row 5. In a copy without that ask rule, it takes effect. It is not saved into the .claude/settings.json you edited: Claude Code saves it to .claude/settings.local.json at the root of the git repository, and it applies to future sessions anywhere in that repository. Four cases keep the file beside day2-work/.claude/settings.json instead, where the reset removes it with the copy: outside a git repository, as in a zip download; on Windows; when the repository root is your home directory; and when the repository root or its .git or .claude entry is not owned by your user. Otherwise the file is at the repository root, which in a clone of this course is the clone's root folder, not day2-work, so the rule outlives the reset and follows you into Day 3's copy. File-edit approvals are never saved; they last until the session ends.

Wherever it lands, .claude/settings.local.json is personal and outranks the shared .claude/settings.json, so a rule that lives only there is one your teammates do not have and will not see in your diff. A rule the team shares is written into the shared file on purpose, where a reviewer gets to ask what it lets through.

One more thing before you grep your own file: Bash(gh pr view *) and Bash(gh pr view:*) are the same rule in two spellings, so searching for one form can miss a rule that is already there.

Part B: what to expect from the connector probes

This course quotes no /mcp or /context output, on purpose. Your connectors do not exist on the machine this course was built on, and the documentation read on 2026-09-22 does not state the format of the context breakdown, so any example printed here would be invented. What you record is your own two figures.

Each attached server's tool names are in the window from the start of the session, with the full schemas deferred by default. This course has not recorded what disabling a server partway through a session does to the figures, so the pair you wrote down is the finding, whatever it shows. If the two figures match, check that /mcp showed the server as attached before you disabled it.

If /mcp shows nothing attached, there is nothing here to measure. Write the honest answer in row 1 of your profile, which is the row that matters most, and move on to Exercise 4.

Swift lane

Kotlin lane
