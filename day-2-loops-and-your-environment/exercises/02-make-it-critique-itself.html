Steps

  1. Read the auditor's frontmatter before you run it. The path is the same in both lanes.

    sed -n '1,6p' .claude/agents/spec-auditor.md

    name is what you type to call it, description says when it applies, and tools: Read, Glob, Grep holds no edit tool, which makes it an auditor rather than a second implementer. model: opus names its model instead of inheriting the session's.

  2. Run /clear. It is not what isolates the auditor: a subagent starts with a fresh, isolated context window and does not see your conversation, the skills you invoked, or the files Claude already read. What reaches it is a delegation message composed by your session; /clear empties that session, so the message comes from your prompt.

    /clear

  3. Invoke the auditor by name and paste this prompt in full. Let it finish without steering it; a critic you argue with mid-run reports your opinion back to you.

    @"spec-auditor (agent)" Audit the working tree against specs/daily-summary.md. For every finding give four things: the criterion number it violates or the token NO-CRITERION, the file and line, the evidence you read, and a one-line fix. Do not edit any file and do not run the tests.

  4. Write your own list into ../work/e2.md before you open anything else: one line per finding, each starting with CRITERION n or NO-CRITERION.

  5. Open the first reveal and score against the six reference findings: how many you hold, and how many you hold that are not on the list. A finding with no file and line is invented, and costs as much as a missed one: ten minutes of routing. Auditing your own Exercise 1 run? The six are the reference tree's defects, so count one as missed only if step 7 turns its test red in your tree.

  6. Route every real finding and write its destination beside it in ../work/e2.md. Fixing code is ring one, which step 8 hands back to the runner; routing is ring two, with Lesson 3's three destinations: a new or sharpened criterion in specs/daily-summary.md, where most NO-CRITERION findings belong; a line in CLAUDE.md for a fact that outlives this change, paid for by removing one of equal weight, or a .claude/rules/<name>.md with paths: globs; or the bin, with a sentence saying why.

    A line routed to CLAUDE.md needs one more edit before the re-run, or the second audit reports your own line: the spec lists CLAUDE.md out of bounds, and its Definition of done names every file the diff may touch. In specs/daily-summary.md, add this line at the end of the out-of-bounds list, and add CLAUDE.md beside run-log.template.md in the Definition of done:

    - Except one line in `CLAUDE.md`, routed there by hand before this run. It is not the runner's change and not a stop.

The six reference findings
#TagWhat it isWhere it shows

3CRITERION 3Days come back oldest firstbyDay returns 2026-03-02 first
4NO-CRITERIONThe order of rows inside a day: the spec never said, the lane's own test did, and the run deleted that test and reversed the rows2026-03-04 comes back LK-013 first
5NO-CRITERIONWhich currencies earn a totals entry was never specified, so declined-only currencies get one2026-03-05 has an EUR entry from LK-017, declined
6CRITERION 4Totals come back in arrival order, not currency-code order2026-03-06 totals read USD, GBP, EUR

Four tagged, two NO-CRITERION. Catching the four and neither of the two is the usual result, and it means the auditor is comparing code to criteria and stopping there; the question it is missing is what the spec did not say that the code had to decide anyway. Fewer than four means it probably could not read what it needed: check that you gave it the spec path and that its tools: line lets it reach the files. More than six, and each extra one needs a file and a line before you route it.

A lost-coverage finding is real, not invented: the deleted test that kept rows inside a day oldest first, the grid's four test names missing from the rewritten summary tests, or checks that compare sets where a criterion asks for an order. That is how findings 3, 4 and 6 stayed green, so count it with those rows.

Where each one goes

Findings 1, 2, 3 and 6 are ring one: fix the code. Each violates a criterion that is already numbered, already binary and already has a test name beside it in the spec's criterion-to-command grid. Nothing about the spec is wrong; the run was. Writing a new rule for a criterion that already exists is how instruction files get long without getting better.

Finding 4 routes to the spec, sharpening criterion 3. The wording the hidden suite was written against: the day order flips, the rows inside a day do not — transactions within a section stay oldest first. Against the spec it is NO-CRITERION: nothing there said which way rows inside a day run. Against the lane it is lost coverage: the shipped summary tests asserted oldest first, and the run deleted that test when it rewrote the file, which is why the reversal stayed green. The sharpened criterion is what stops the next run deleting it for free.

Swift lane

The deleted test is testTransactionsInsideASectionAreOrderedOldestFirst in Tests/LedgerKitTests/LedgerSummaryTests.swift.

Kotlin lane

The deleted test is a section is ordered by postedAt within the day in src/test/kotlin/ledgerkit/LedgerSummaryTest.kt.

Finding 5 routes to the spec, sharpening criterion 4. Add the clause the criterion was missing: no entry for a currency with no posted and no pending row that day. This is the one most people bin as a detail, and it is the one that puts an empty EUR line on a customer's statement. If you put the clause under criterion 1 instead, because the stray entry came from declined rows, that routing is just as right: what matters is that the clause lands in the spec.

Finding 1 also earns the day's one line in CLAUDE.md. The criterion covers this change; the domain rule underneath it — a declined transaction counts toward no total and still appears in the list — is what the next money change will meet again, on a spec nobody has written yet. That is the test for a standing line: not whether it is true, but whether it outlives the spec that produced it.

The reference CLAUDE.md revision, paid for

One line in, two lines out, in both lanes. The sentence that goes in is the same one; what pays for it is whatever that lane's file was already spending those two lines on. The same revision is in the repository at starter/reveal/claude-md-diff.md.

Swift lane

In, under ## Money, where the other domain rules already are:

A declined transaction is still listed and counted in no total; pending money is reported separately from settled money.

Out, from ## Engineering principles, items 9 and 11:

9. Leave the campsite cleaner than you found it.
11. Premature optimization is the root of all evil.

This file carries no statuses line to sharpen, so the new rule is paid for by two principles that name no specific mistake.

Kotlin lane

Out, from ## Domain rules, the two-line statuses bullet:

- Statuses are `pending`, `posted` and `declined`. A declined transaction is
  still a transaction and is still shown to the customer.

In, one line in its place:

- Statuses are `pending`, `posted` and `declined`. A declined transaction is still listed and counted in no total; pending money is reported separately from settled money.

The bullet that comes out is true, and it is the half of the fact the code does not get wrong. The half it gets wrong is the money.

Two lines out and one in, so wc -l CLAUDE.md goes down by one, which is why net-zero is written as same or lower rather than as exactly equal. The arithmetic is not the test, though: ask of each line what specific mistake its removal would cause. The added line names one you watched happen this morning, in a run that was green when it happened.

The alternative the reference run considered and rejected: put the same rule in .claude/rules/money.md with paths: ["**/Money*", "**/LedgerSummary*"] in its frontmatter, so it loads when Claude reads a matching file, not on every tool use. Rejected because the rule is one sentence long and the files it would be scoped to are the ones this module mostly edits, which buys a file and saves nothing.
