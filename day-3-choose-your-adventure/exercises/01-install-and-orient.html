Install your track and map what it wrote

Day 3: Choose your adventure · Exercise 1 of 3 · 25 min

By the end you will have your chosen framework installed and initialized in day3-work, a fresh copy of your LedgerKit lane, and a five-line ../work/map.md you wrote yourself from the files: where specs live, what creates one, what implements one, what happens after ship, and every file the tool touched outside its own folder.

Setup

Paste one block from the course root. It makes work/ for your answers, copies your lane to day3-work, moves you into it, and copies in the Change C brief and the blank map as ../work/map.md, never over a map you have started. If day3-work already exists, run rm -rf day3-work first: cp -R into an existing folder nests a second copy inside it.

Swift lane 
mkdir -p work && cp -R sandbox/swift day3-work && cd day3-work
cp ../day-3-choose-your-adventure/starter/change-c-brief.md .
{ [ -f ../work/map.md ] || cp ../day-3-choose-your-adventure/starter/map-template.md ../work/map.md; }
ls change-c-brief.md ../work/map.md
Kotlin lane

The block prints ../work/map.md and change-c-brief.md. day3-work is the day's project root, the folder holding CLAUDE.md, and your framework is initialized in it. Setup blocks are pasted from the course root; every other Day 3 command runs from inside day3-work; the starters are at ../day-3-choose-your-adventure/starter/ and arrive one file at a time, so your framework never reads its own answer key.

The shipped sandbox/ is never edited, so it is your before-picture: what a track wrote is a diff of this folder against it. Keep two terminal tabs in day3-work, one for the shell and one for Claude Code, started there with claude.

Steps

Steps 2 to 4 depend on your track; pick its tab.

OpenSpec

  1. Check the runtime in the shell tab. OpenSpec's package requires Node 20.19.0 or higher.

    node --version

    v20.19.0 or higher passes. Anything lower: upgrade Node or switch tabs; the offline snapshot cannot run OpenSpec without it.

  2. Install the CLI and confirm the version.

    npm install -g @fission-ai/openspec@1.13.1
openspec --version

    It prints 1.13.1, the version this page was checked against on 2026-09-22.

    Can't install globally? Skip this step and put npx -y @fission-ai/openspec@1.13.1 wherever this tab says openspec; step 4's init becomes npx -y @fission-ai/openspec@1.13.1 init --tools claude, which picks Claude Code for you. The /opsx commands call openspec by name, so if Claude reports it missing, tell it to use the same npx form.

  3. Initialize it in day3-work, the folder you are standing in, not the course root. When it asks which tools to set up, choose Claude Code.

    openspec init
openspec list

    Success is 6 skills and 6 commands in .claude/ in the init summary, then No active changes found. from openspec list, which is what a freshly initialized project looks like.

    The first run also prints a note that OpenSpec collects anonymous usage stats, and writes ~/.config/openspec/config.json holding an anonymous id. That file sits outside day3-work, so step 5's diff cannot see it and neither map will list it unless you add it. To opt out, run export OPENSPEC_TELEMETRY=0 in both tabs before openspec init, restarting claude after it so the /opsx commands inherit it; then init prints no note and writes no file there.

If you see something else instead

Likely wrong turns

  • The diff names only change-c-brief.md after a successful install. The framework was initialized elsewhere, usually the course root, where ls -a .. shows an openspec/, _bmad/, _bmad-output/ or docs/ beside sandbox/, and on the LID tab an AGENTS.md, with a CLAUDE.md link to it, holding a ## LID section. Delete those, and under the course root's .claude/ delete only the framework's entries: commands/opsx/, skills/openspec-* or skills/bmad-*. Then initialize again inside day3-work.
  • Unknown command: /arrow-maintenance:map-codebase on the LID tab means this session has not loaded the plugin. Quit, start claude again in day3-work, and retry; if it is still unknown, use the network-blocked start.
  • The BMAD installer's directory field does not end in day3-work. You launched it from another folder; quit it, cd into day3-work, and run it again.
  • On the LID tab, Only in ./.claude: settings.local.json in the diff. If you answered “Yes, and don't ask again” to a command in a download without git, Claude Code saved that rule to .claude/settings.local.json in day3-work (in a clone, at the repository root). It belongs in line 5.
  • A second failure in the known-issue run means the install wrote into source; the command in your lane's box below shows where.

Self-check

Three checks decide it

First, the plain suite: your lane's test command from step 1 again, with the same result and the same count. Second, the known-issue run fails on exactly one test, the JPY case.

Swift lane 
LEDGER_RUN_KNOWN_ISSUES=1 swift test

The error line names testLEDGER7_JPYRendersWithTwoDecimalPlaces, and the verdict reads:

Test Suite 'All tests' failed at ….
	 Executed 34 tests, with 1 failure (0 unexpected) in … (…) seconds
Kotlin lane 
LEDGER_RUN_KNOWN_ISSUES=1 ./gradlew test

The verdict line is BUILD FAILED in …; above it:

KnownIssueTest > LEDGER-7 the JPY row renders with decimal places it should not have() FAILED
…
85 tests completed, 1 failed

Third, every path the diff names appears in your own answers. The mine= line reads sections 1 to 5 of your map, not the agent's block; the loop prints one line per path, ok or MISSING. A folder counts only with its trailing slash, as in openspec/, so naming the tool is not the same as naming its folder.

mine=$(sed -n '/^## 1\./,/^## The agent/p' ../work/map.md)

  grep -vx 'change-c-brief.md' |
  while read -r p; do
    [ -d "$p" ] && p="$p/"
    if printf '%s\n' "$mine" | grep -qF -- "$p"; then echo "ok       $p"; else echo "MISSING  $p"; fi
  done
